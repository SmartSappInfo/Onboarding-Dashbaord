## 1. Executive Summary & Objective

In autonomous agent swarms, durable workflows, and MCP tool execution pipelines, high-risk operations (mutating CRM records, dispatching outbound communications, allocating financial resources, modifying access policies, or executing privileged actions) cannot proceed without explicit, cryptographically verifiable human consent (**Rule 21: Two-Phase Action Model**).

The objective of **Phase 8 Milestone 3** is to build the production-grade **Unified Agent Approval Center** (`/admin/intelligence/approvals`), providing human operators with an unassailable mission control desk to inspect, review, verify, and adjudicate pending action proposals generated by autonomous agents, swarms, and durable workflows.

### Core Architectural Pillars & Invariants:
1. **Rule 13: Model Distrust & Anti-Self-Approval Enforcement:** Requester cannot approve their own high-risk actions; dual-authorization required for L4 privileged actions.
2. **Rule 18: Live TOCTOU Authority Check:** Live check verifies the approving operator's active permissions before granting execution authority.
3. **Rule 21 & 22: Two-Phase Approval & Cryptographic Hash Binding:** Validates canonical key-sorted SHA-256 `payloadHash` at decision time; execution fails closed with `PAYLOAD_TAMPERED` if any bit of the proposed payload is modified.
4. **Rule 27: Sagas & Compensation Trigger on Rejection:** Rejecting a proposal automatically triggers reverse-LIFO compensating capabilities for already-executed steps in the parent agent run.
5. **Rules 13 & 30: Untrusted Reference Data Isolation:** Dynamic payload contents, parameters, and evidence packs are rendered strictly within `<UntrustedReferenceData id="...">` XML boundaries.
6. **Rule 40 & 41: State History Audit Trail & Explainability Standard:** Eliminates vague AI summaries in favor of the structured 6-section explainability grid: **WHAT, WHY, AFFECTED ENTITIES, BLAST RADIUS, EVIDENCE, EXPECTED CHANGE**.
7. **Rule 60: Emergency Dead-Man Switch Gate:** Live governance dead-man pause check blocks approval executions during active platform emergencies, returning HTTP 503 `DEAD_MAN_PAUSED`.
8. **Rule 62: Real-Time SSE Reactivity:** Real-time updates via `useEventStream` subscribing to `policy.approval.*`, `agent.run.approval_required`, and `governance.dead_man.*` without client polling.
9. **Rule 69: Strangler Fig Pattern SSOT:** Seamless backward compatibility redirect from `/admin/approvals` to `/admin/intelligence/approvals` preserving query parameters.
10. **Standardized Modal Architecture (`theme.md` §8):** The `ProposalReviewDrawer` and `RejectApprovalModal` strictly adhere to demarcated headers, single-circle `<CardInfoTooltip text="..." />` at `z-[10050]`, screen-reader descriptions, and demarcated footers with tactile buttons (`rounded-xl active:scale-[0.97]`).

## 2. Threat Modeling, Failure Modes & Edge Case Analysis

| Threat / Failure Mode | Root Cause | Impact | Mitigation in Milestone 3 |
| :--- | :--- | :--- | :--- |
| **Payload Tampering / MITM** | Parameter alteration between agent proposal and execution | Malicious or unintentional mutation applied to production database | **Rule 22 Cryptographic Hash Binding:** `payloadHash = sha256(canonicalJsonStringify(payload))`. At approval execution time, the payload is re-hashed. If there is a 1-bit discrepancy, execution fails closed with `PAYLOAD_TAMPERED`. |
| **TOCTOU Authority Drift** | Operator had permissions when proposal was queued, but privileges were revoked before approval | Unprivileged operator approves high-risk actions | **Rule 18 Live TOCTOU Verification:** In `approveActionProposalAction`, active user roles and permissions are queried in real time, failing closed with `UNAUTHORIZED_APPROVER` if revoked. |
| **Self-Approval Privilege Escalation** | An operator running an autonomous agent approves their own high-risk proposal | Bypass of dual-control compliance controls | **Rule 13 Anti-Self-Approval:** The system asserts `proposerId !== approverId` for critical or L4 privileged capabilities. Proposers are forbidden from approving their own actions. |
| **Replay Attacks & Burn Avoidance** | Malicious replay of an already-approved proposal ID | Duplicate financial transactions or messaging spam | **Single-Use Binding State Machine:** Proposals transition atomically: `pending -> approved -> bound`. A proposal can only be executed once. Subsequent attempts throw `PROPOSAL_ALREADY_BOUND`. |
| **Indirect Prompt Injection in Payloads** | Untrusted external data contains adversarial instructions (e.g., `<script>` or LLM override tags) | Operator UI compromise or downstream LLM poisoning | **Rules 13 & 30 XML Isolation:** All dynamic payload attributes and evidence are rendered inside `<UntrustedReferenceData id="...">` containers, preventing DOM and LLM script injection. |
| **Emergency Dead-Man Lockdown Bypass** | Operator attempts to approve high-risk actions during a systemic platform incident | Uncontrolled mutations during disaster recovery | **Rule 60 Gate:** `checkGovernanceDeadManSwitch(organizationId)` is evaluated before every approval mutation, failing closed with HTTP 503 `DEAD_MAN_PAUSED`. |
| **Mobile & Touch Inaccessibility** | Tiny buttons, clipping modal tooltips, or missing focus states | Operator errors on mobile/tablet devices | **`theme.md` §8 & Rule 7 Standards:** All buttons meet `min-h-[44px]` with `active:scale-[0.97]`. Tooltips elevate at `z-[10050]`. Responsive drawer layouts adapt smoothly to mobile viewports. |
